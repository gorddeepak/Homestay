## Authentication endpoints and contracts

All endpoints are under `/api` and use JSON.

| Endpoint | Success | Main failures |
| --- | --- | --- |
| `POST /api/auth/signup` | `201` with `{id, username, email}` and `Set-Cookie` | `409` duplicate username, `422` validation, `403` origin, `429` rate limit, `503` database |
| `POST /api/auth/login` | `200` with `{id, username, email}` and `Set-Cookie` | `401` generic invalid credentials, `403` origin, `429` rate limit, `503` database |
| `POST /api/auth/logout` | `200` with `{ok: true}` and an expired auth cookie | `403` origin |
| `GET /api/auth/me` | `200` with `{id, username, email}` | `401` missing/invalid/expired/tampered token or missing user, `503` database |

Request bodies:

```json
{ "username": "alice", "email": "alice@example.com", "password": "Password123!" }
```

```json
{ "username": "alice", "password": "Password123!" }
```

The public user response contains only `id`, `username`, and `email`. Password
salts, hashes, sessions, and other private fields are never returned. The
current user is always resolved from the signed cookie, never from a
client-supplied id.

## Password compatibility strategy and evidence

The installed plugin is `passport-local-mongoose` 9.1.0. Its installed source
was inspected directly:

- `saltlen: 32`, `iterations: 25000`, `keylen: 512`,
  `digestAlgorithm: "sha256"`, `encoding: "hex"`.
- A salt is generated as 32 random bytes and stored as a 64-character hex
  string.
- The hash is the 512-byte PBKDF2 result stored as 1024 hex characters.
- The plugin passes the **hex salt string** to `crypto.pbkdf2` as a JavaScript
  string. Node therefore uses the UTF-8 bytes of that text as the salt. Python
  uses `salt.encode("utf-8")`; it does **not** decode the hex into 32 bytes.

Python generates new credentials with:

```python
salt = secrets.token_hex(32)
digest = hashlib.pbkdf2_hmac(
    "sha256",
    password.encode("utf-8"),
    salt.encode("utf-8"),
    25_000,
    dklen=512,
)
stored_hash = digest.hex()
```

Verification uses `hmac.compare_digest`. Unknown usernames still perform a
dummy PBKDF2 calculation so the response time is not a simple existence
oracle. Login never rewrites a stored hash or salt.

Evidence from the tests:

- A hash generated by the actual installed Node plugin is verified by Python.
- Reusing that plugin-generated salt in Python produces the exact same hash.
- The same checks pass with a non-ASCII password, covering UTF-8 handling on
  both sides.
- A user created through `POST /api/auth/signup` authenticates successfully
  through the actual Node `User.authenticate()` method.
- The same user is rejected by Passport Local with a wrong password.
- A successful FastAPI login leaves the stored `salt` and `hash` byte-for-byte
  unchanged.
- Login accepts existing usernames and passwords without new upper length
  bounds, so longer legacy credentials remain usable.

## Cookie, JWT, origin/CSRF, and rate-limiting decisions

### JWT and cookie

- PyJWT with `HS256`.
- Claims: `sub` (MongoDB ObjectId string), `iat`, and `exp`.
- Seven-day expiration. `exp` and `sub` are required when decoding.
- Secret comes only from `AUTH_JWT_SECRET`; there is no hard-coded or fallback
  secret. The app refuses to start if it is shorter than 32 characters.
- Cookie name: `homestay_auth`.
- Cookie attributes: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=604800`,
  and no `Domain` attribute. `Secure` is controlled by `AUTH_COOKIE_SECURE`
  (false for local HTTP development, true for production HTTPS).
- Logout clears the same cookie with `Max-Age=0`.

`422` validation responses are sanitized to remove submitted values, so a
password from a rejected signup request is not echoed back to the client.

The cookie is separate from Express's `connect.sid`. There is intentionally no
session bridge; users may need to sign in separately to the React and EJS
applications.

### Origin/CSRF protection

`require_trusted_origin` is a reusable FastAPI dependency. It requires an
`Origin` header that exactly matches one of the configured
`AUTH_ALLOWED_ORIGINS`. Missing or untrusted origins receive `403`. It does not
trust arbitrary `Host` or `X-Forwarded-Host` headers.

It is applied to signup, login, and logout. Future state-changing endpoints
should reuse the same dependency. `SameSite=Lax` is an additional layer; this
is origin validation rather than a per-request CSRF token.

Local development defaults to:

```text
http://localhost:5173,http://127.0.0.1:5173
```

The production frontend origin must be added explicitly. The API and frontend
are expected to be same-origin in production; the existing Vite `/api` proxy
is used in development, so no CORS configuration was added.

### Rate limiting

slowapi 0.1.9 is used with its in-memory storage:

- Signup: 5 requests per minute per remote address.
- Login: 10 requests per minute per remote address.
- Exceeded limits return `429` with a JSON error.

Important limitations:

- Counters are per process. Multiple Uvicorn workers or multiple API instances
  do not share counters.
- Restarting the process clears the counters.
- `get_remote_address` uses the direct client address. Behind a proxy, all
  users may share the proxy address unless trusted proxy handling is
  configured deliberately.
- This is basic abuse protection, not account lockout, a WAF, or a distributed
  quota system.

A shared rate-limit store (for example Redis) and proxy-aware client-address
handling are deferred to deployment-hardening work.

## Environment variables and local run instructions

Add these to `backend/.env` (copy `backend/.env.example`):

| Variable | Required | Purpose |
| --- | --- | --- |
| `ATLAS_DB_URL` | Yes | MongoDB connection string including the database name. |
| `AUTH_JWT_SECRET` | Yes | Secret used to sign auth cookies; at least 32 characters. |
| `AUTH_COOKIE_SECURE` | No | `false` for local HTTP; `true` in production HTTPS. Defaults to false. |
| `AUTH_ALLOWED_ORIGINS` | No | Comma-separated browser origins allowed for state-changing auth requests. Defaults to the two local Vite origins. |

Generate a local secret with:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Run the backend:

```powershell
cd backend
Copy-Item .env.example .env
# edit .env: set ATLAS_DB_URL and AUTH_JWT_SECRET
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

Run the React frontend and the existing Express app in separate terminals:

```powershell
cd frontend
npm install
npm run dev
```

```powershell
# repository root
npm start
```

Vite proxies `/api` to FastAPI on `127.0.0.1:8000` and `/images` to Express on
`127.0.0.1:8080`. The backend reads only `backend/.env`; the root `.env`
continues to serve the Express application.

For production, use HTTPS, set `AUTH_COOKIE_SECURE=true`, set
`AUTH_ALLOWED_ORIGINS` to the real frontend origin, and provide a strong
`AUTH_JWT_SECRET`. Do not commit `.env` files or real secrets.

## Known limitations

- Authentication is a stateless seven-day JWT. Logout clears the cookie, but a
  copied token remains valid until expiration; there is no server-side token
  revocation list or refresh-token rotation.
- Rate limiting is in-memory and per process, as described above.
- The existing schema has a unique username index but no unique email index.
  Duplicate emails remain allowed, matching current Express behavior.
- Login is by username only, matching the existing Passport Local setup.
  Email cannot be used as a login identifier.
- Usernames remain case-sensitive and are not lowercased, matching the
  installed plugin defaults.
- New FastAPI signups require an 8-character minimum password (at most 128
  characters) and a username of at most 50 characters. Existing accounts and
  the Express signup form are unchanged; existing short passwords can still log
  in because login has no new upper bounds.
- Pydantic `EmailStr` rejects special-use/reserved domains such as `.test` for
  new signups. Existing user records are not revalidated.
- The app assumes a same-origin production deployment. A cross-origin frontend
  would require a deliberate CORS and cookie plan and is out of scope.
- Origin validation plus `SameSite=Lax` is the CSRF defense. There is no
  per-request CSRF token.
- There is no account lockout, email verification, password reset, OAuth, or
  account recovery.
- No auth audit logging was added.
